Verified workflow integration

Durable Shopify order intake, tested duplicate handling, recoverable ERP delivery, and verified Gmail and WhatsApp notifications.

Signed Shopify orders are validated and stored in PostgreSQL, then delivered through scheduled n8n workflows. Database functions control atomic intake, job claims, lease-checked completion, retries and notification outboxes. The default delivery workflow uses mock ERP; a separate Odoo QA branch was tested with a real development-store order.

  • Real Shopify → Odoo. Order #1018 became draft quotation S00048. Replaying the signed webhook created no duplicate.
  • Recovery tested. Concurrent intake, scheduled retries, dead-letter recovery, mock crash reconciliation and restart persistence passed.
  • WhatsApp delivery verified. Meta accepted the custom alert template, and I confirmed receipt. After template approval, I also activated and tested the failure-notification workflow successfully.

The default demonstration uses mock ERP. The real Odoo integration was tested separately with a draft quotation; the QA report records the tested scope and remaining limitations.

Verified business outcome

Real Shopify order #1018 passed authenticated intake and reached Odoo draft quotation S00048 on its first delivery attempt. Exact signed replay created no second order, job or quotation. The quotation remained draft: no confirmation, stock movement or invoice was issued.

The source/local total and Odoo subtotal were USD 222.00. Odoo's existing 15% tax added USD 33.30, producing USD 255.30. This was a documented tax-configuration difference, not a claim of tax-inclusive financial parity. The Python API's later USD 60.00 confirmed-order test is a separate result.

Reliability and recovery tested

  • Raw-body HMAC validation and actual signed webhook acceptance/rejection.
  • SQL-level atomic-intake rollback when the second line was invalid.
  • Eight overlapping signed requests yielding one accepted order/job/receipt and seven duplicate replies, followed by one mock ERP outcome.
  • Controlled transient failures followed by scheduled delivery on attempt three; retry exhaustion into a dead job; privileged manual recovery with an audit reason and subsequent successful delivery.
  • Overlapping worker execution, lease checks, mock post-create crash reconciliation, and persistence/replay after a graceful PostgreSQL restart.

The SQL rollback check, actual workflow executions, mock fault tests and real Odoo delivery are distinct evidence layers. Mock fault recovery is not presented as proof of every possible real Odoo failure.

Notifications verified

Historical Gmail and WhatsApp executions and outbox records cover successful sending and controlled failure/retry paths. The custom WhatsApp failure-alert template was accepted by Meta, and I confirmed receiving the test message. After template approval, I also activated and tested the failure-notification workflow successfully.

The direct template-send test and my subsequent workflow test are documented separately in the verification record. A later inactive local workflow snapshot does not undo those completed tests or establish continuous operation.

Verification coverage

Retained integration tests cover reliability and a real Shopify order. Clean-volume Compose/database bootstrap and migrations were verified, and the custom WhatsApp template-send result and recipient receipt were recorded. The later post-approval workflow test is retained with owner-reported provenance; its exact execution ID and activation time were not established by the review.

A read-only review checked all 23 stored business orders and their 137 audit events. All 23 had succeeded delivery jobs; 22 retained one mock outcome each, while the real Odoo fixture retained its separate ERP reference. All 37 execution IDs selected from the existing QA references were present. These records corroborate the retained tests; execution counts are not advertised as automated test counts.

Scope

This implementation uses n8n and PostgreSQL. It has no verified AWS deployment in the retained evidence; the Python API's AWS results are separate. Odoo was tested as a draft-quotation branch, and its lookup-before-create does not guarantee atomic external uniqueness. Governed approvals, cancellations and shipment/stock operations belong to the Python API, not this n8n project. Fresh-instance workflow import, an actual n8n backup restore, broader real Odoo fault/concurrent-create cases and permanent Meta-error classification remain outside the verified scope.
