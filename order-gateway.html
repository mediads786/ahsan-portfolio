Portfolio case study

ERP Order Integration Gateway: Shopify-to-ERP delivery with operational controls

The problem

When an ERP is unavailable or a webhook arrives more than once, operators need more than a success message: they need durable records, controlled retries and a clear history of what happened. Drawing on 25+ years in operations, I built Order Gateway to make order delivery visible and recoverable, with authorization for sensitive changes.

What I built

  • Signed Shopify orders/create intake that verifies the HMAC over the original request body and refuses unsigned or tampered requests. Invalid orders retain rejection reasons.
  • Atomic PostgreSQL persistence for accepted orders, their delivery jobs and intake audit events. Decimal arithmetic preserves the supported line amounts and computes order totals.
  • Duplicate detection using request identity and a stored payload hash. Recorded same-ID replay tests reused the existing order and job; a changed payload using that ID was refused. A separate sequential Odoo replay retained one ERP order.
  • A separate Python worker with automatic retries, exponential backoff with jitter, dead-letter handling, stale-job recovery and manual retry. The worker delivers accepted orders through the selected ERP adapter and marks successful delivery as CONFIRMED.
  • Mock ERP and Odoo 19 Community adapters. Recorded local Odoo tests cover sales-order confirmation, approval-governed cancellation and stock adjustment, and signed stock reduction with replay and insufficient-stock checks.
  • Admin pages for order status, attempts, errors and history, with views of approvals and proposals. API-key roles govern sensitive actions; cancellation and stock adjustment require approval by a different key. The governed order-creation route can hold large orders for approval. Natural-language requests produce proposals for human confirmation; the default proposer is rule-based.

Verified integration outcomes

  • Real Shopify-to-Odoo confirmation. Shopify development-store order #1021 reached confirmed Odoo sales order S00054 with matching BOOK/PEN quantities, prices and a USD 60.00 total. The gateway job completed on its first attempt.
  • Delivery recovery. Recorded mock-ERP tests demonstrate normal delivery, recovery after controlled HTTP 500 failures and exact-request replay. A separate retained history demonstrates terminal failure, manual requeue and successful recovery without removing the earlier events.
  • Odoo replay. A synthetic signed Shopify-to-Odoo test confirmed delivery and retained one ERP order when the identical webhook was replayed sequentially.
  • Record reconciliation. A read-only review covered all 56 stored local API orders and their 264 audit events. All currently confirmed orders had completed jobs and confirmation events; stored line sums matched order totals wherever lines existed. This review corroborated retained evidence rather than submitting new orders.

AWS deployment and recovery checks

Docker Compose runs the services behind Caddy, which provides trusted HTTPS, HTTP-to-HTTPS redirection and security headers. Caddy is the only container publishing application ports. Recorded checks cover admin/API authentication, secure session-cookie flags, host firewall, container health checks, restart policies, log rotation and IMDSv2.

The deployment smoke test passed HTTPS, authentication and a signed sample order reaching CONFIRMED through the mock ERP. Same-webhook replay reused the existing order and job with one mock outcome; invalid signatures and conflicting payload reuse were refused. The USD 10.00 fixture retained its amount through the gateway and mock ERP.

Nightly database backup checks covered scheduling, restricted permissions and gzip integrity. A backup was restored into a temporary database on the same host, with matching row counts across all 11 copied tables. Credential rotation was followed by rejection of the old credentials and a successful backup using the replacement database credential. No credential values or deployment addresses are published.

Regression evidence

Recorded local and CI regression runs each passed 284 tests, with one optional live-Odoo test skipped. GitHub Actions runs the suite on pushes to master and pull requests. These are retained test results; the evidence reconciliation did not rerun the suite.

Scope

This is a demonstrated integration system with scoped test results. Local Odoo confirmation and the AWS mock-ERP deployment are separate verified outcomes. Tax calculation sync, general tax/discount/shipping reconciliation and full warehouse fulfilment are outside scope. The admin login is shared; the approval threshold applies to governed order creation, not every intake route. Replay tests demonstrate the recorded paths, not unconditional exactly-once external effects. Known concurrency limits are documented in the verification summary. High availability, sustained-load capacity, off-server backups and replacement-host recovery were not established by the recorded deployment checks.

Gmail and WhatsApp notifications belong to the separate n8n implementation; the Python API provides failure visibility and audit history.
